Hexo Butterfly字体图标偶尔不显示的解决方案和FontAwesome本地化配置

发表于2026-11-20|更新于2026-11-20|hexo

问题背景

在使用 Hexo Butterfly 搭建个人博客的过程中，笔者遇到过一个比较奇怪的问题：博客在本地预览时，部分字体图标显示正常，但是经过生成、部署后，偶尔会出现字体图标无法显示的情况。

不要去他们官网下载字体库，那边好像需要收费，你直接使用笔者下方提供的github那边web字体就可以用。

具体表现为：

  • 网站菜单中的部分图标无法正常显示。
  • 文章中的功能图标偶尔变成空白。
  • 公告、社交媒体等位置的图标显示异常。
  • 有时候刷新页面能够恢复，有时候却依然无法显示。

一开始，笔者怀疑是第三方 CDN 网络不稳定，导致字体文件没有正常加载。但在进一步排查的过程中，笔者注意到了一个细节：页面实际渲染的字体图标代码是：

这段代码使用了 fas、fa-bullhorn 和 fa-shake 等 Font Awesome 图标类名。

笔者由此产生了一个怀疑：当前项目中使用的字体图标资源，是否混用了不同版本的 Font Awesome 文件？

例如，CSS 样式文件来自一个版本，而底层字体文件却来自另一个版本。不同版本的图标名称、字体定义和兼容规则可能存在差异，如果混合使用，就可能导致部分图标无法正确渲染。

当然，这只是笔者根据现象作出的排查判断，并不能直接认定所有图标异常都是版本混用导致的。

为了彻底排除旧资源干扰，笔者决定不再局部修补，而是对原有字体图标资源进行一次彻底清理，重新下载一套完整的 Font Awesome 资源，将 CSS 样式文件和字体文件统一替换为同一版本，并改为本地加载。

六、验证字体图标是否正常加载

部署完成后，打开线上博客，检查菜单、公告、社交媒体以及文章中的字体图标。

如果仍然存在图标无法显示的情况，可以通过浏览器开发者工具进一步排查。

重点关注：

  1. all.min.css 是否成功加载。
  2. 字体文件是否成功加载。
  3. 字体文件请求是否返回 HTTP 200。
  4. 是否还存在对旧版第三方字体 CDN 的请求。
  5. 是否出现 404、字体加载失败等错误。

如果 CSS 加载成功，但字体文件返回 404，优先检查 css 和 webfonts 的目录结构，以及 CSS 内部的相对路径是否正确。

如果 CSS 和字体文件都正常加载，但个别图标依然无法显示，则需要进一步检查图标类名是否受当前 Font Awesome 版本支持，以及是否存在其他 CSS 样式冲突。

七、总结

这次解决 Hexo Butterfly 字体图标偶尔不显示的问题，笔者并没有只针对某一个图标进行修补，而是从实际渲染出来的 HTML 图标代码入手，怀疑原有项目可能存在不同版本 Font Awesome 资源混用的情况。

为了排除旧资源干扰，笔者从 Font Awesome 官方 GitHub Releases 下载了完整的 fontawesome-free-7.3.1-web.zip，然后清理旧资源，将新的 all.min.css 和 webfonts 字体文件统一替换到 Butterfly 主题目录中。

整个操作最重要的地方有两个：

  • 目录位置不能弄错： 文件需要放在 themes/butterfly/source 中，而不是 Hexo 项目根目录下的 source。
  • 目录结构不能弄乱： css/all.min.css 和 webfonts 必须保持正确的相对关系，否则 CSS 无法找到对应的字体文件。

完成替换后，再通过 _config.butterfly.yml 引入本地 CSS，重新生成并部署博客，就可以让字体图标资源由主题统一管理，减少对第三方 CDN 的依赖。

对于 Hexo Butterfly 博客来说，将字体图标 CSS 和字体文件统一本地化，是一种比较直接、方便维护的处理方式，也能有效减少第三方网络资源加载异常带来的影响。

当然，本地化并不意味着以后绝对不会出现图标加载问题，仍然需要保证 CSS、字体文件和部署路径正确。但至少可以避免因第三方字体 CDN 不稳定而导致的这一类问题。
